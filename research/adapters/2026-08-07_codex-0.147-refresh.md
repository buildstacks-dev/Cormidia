# Codex harness refresh — @openai/codex 0.144.4 → 0.147.0

*2026-08-07. Issue [#335](https://github.com/cormidia/Cormidia/issues/335) (epic
#330), Codex slice. Procedure: `docs/harness/adding-updating.md` §6 (re-read
vendor docs → bump → re-certify → re-check tiers → dated research record) and §5
(standalone certification ladder). Supersedes the Codex vendor facts — not the
decisions — in `research/adapters/2026-08-06_adapter-upstream-references.md`.*

**Outcome: certified.** Pin moved to exactly `0.147.0`, live L3 walk green with
an empty `violationIds`, no capability tier moved, and one real fail-open gate
defect was found and fixed with an offline detector (CF-REG-335).

`0.147.0` is the newest non-prerelease `0.147.x` on npm (`npm view @openai/codex
version` → `0.147.0`; `0.148.0-alpha.{1,2}` exist but are prereleases).

The **floor is deliberately not raised**. A floor is an interface claim, not a
copy of the pin: nothing in this refresh proved the adapter stopped speaking
0.144.4's interface, so raising it would refuse operators who have not upgraded —
exactly what version bands exist to avoid (#331). The real per-adapter floor is
research owed with #224.

`pnpm-workspace.yaml` gained `minimumReleaseAgeExclude` entries for `0.147.0` and
its six platform-tagged payloads: the version was published the same day it was
pinned, so it is younger than the configured minimum release age. pnpm generated
one combined range string; it was rewritten as one entry per version to match the
file's existing convention, and re-verified with
`pnpm install --offline --frozen-lockfile --ignore-scripts --verify-store-integrity`.

## 2. Vendor documentation re-read (step 1)

- App Server — <https://learn.chatgpt.com/codex/app-server>
- Config reference — <https://learn.chatgpt.com/codex/config-file/config-reference>
- Releases — <https://github.com/openai/codex/releases> (0.145.0, 0.146.0, 0.147.0)

Relevant statements:

- App Server remains the documented surface for "deep integration inside your own
  product: authentication, conversation history, approvals, and streamed agent
  events" — Cormidia's exact consumption. No change to the recommendation.
- 0.147.0 removes `codex exec --full-auto` ("use `--sandbox workspace-write`
  instead"). **Cormidia never used it** — `grep -rn "full-auto\|full_auto"` over
  `src/`, `tests/`, `scripts/`, `docs/` returns only the prose note in
  `research/adapters/2026-08-06_adapter-upstream-references.md`. No action.
- The config reference documents `features.code_mode` in **table** form
  (`.enabled`, `.direct_only_tool_namespaces`, `.excluded_tool_namespaces`). The
  binary still accepts the boolean form: `codex --help` documents
  `--disable <FEATURE>` as "Equivalent to `-c features.<name>=true|false`", and
  `codex features list` renders `code_mode` as a single flag. Cormidia's
  `-c features.code_mode=false` remains valid (proved by the live walk).
- The App Server doc page renders `approvalPolicy` values as
  `never | onRequest | unlessTrusted`. **The generated protocol schema
  contradicts the prose**: `AskForApproval` is `["untrusted", "on-request",
  "never"]` (kebab-case) in both 0.144.4 and 0.147.0, and a real `thread/start`
  echoed back `"approvalPolicy": "on-request"`. Cormidia's kebab-case value is
  correct; the doc page is wrong. Recorded so the next refresh does not "fix" it.

## 4. Per-workaround verdicts

### (a) Trust-bypass flag dropped by `app-server` dispatch — **KEEP (unproven obsolete)**

Cormidia supplies the bypass twice: the public CLI flag
`--dangerously-bypass-hook-trust` in `codexAppServerArgs()`, and the typed
`config.bypass_hook_trust: true` on the thread request in `threadParams()`.

Evidence on 0.147.0:

- The flag still exists and is still documented at the top level: `codex --help`
  → "Run enabled hooks without requiring persisted hook trust for this
  invocation."
- It is still **absent** from `codex app-server --help`'s option list —
  consistent with the original 0.144.4 finding that app-server dispatch does not
  forward it into `ConfigOverrides`.
- `hooks/list` **cannot discriminate**. Across all four combinations (flag only /
  config only / both / neither) the per-turn hook is reported identically:
  `source: "sessionFlags"`, `enabled: true`, `trustStatus: "untrusted"`. That
  field reports the *persisted* trust record, which an ephemeral per-turn hook
  never has; the bypass is applied at hook-execution time and is not observable
  without a tool call, i.e. without a paid turn.
- `thread/start` accepted `config.bypass_hook_trust: true` without error and
  echoed no resolved hook-trust state.

**Neither mechanism can be proven redundant token-free, so both stay.** The live
walk (§5) is the end-to-end proof the *combination* still works: both forbidden
actions reached Cormidia's in-process gate and were terminally denied.

### (b) Private model-catalog clone with `tool_mode` cleared + Responses Lite disabled — **KEEP (still load-bearing)**

`codex debug models --bundled` is byte-identical in the fields that matter:

| slug | 0.144.4 `tool_mode` / `use_responses_lite` | 0.147.0 `tool_mode` / `use_responses_lite` |
| --- | --- | --- |
| `gpt-5.6-sol` | `"code_mode_only"` / `true` | `"code_mode_only"` / `true` |
| `gpt-5.6-terra` | `"code_mode_only"` / `true` | `"code_mode_only"` / `true` |
| `gpt-5.6-luna` | `"code_mode_only"` / `true` | `"code_mode_only"` / `true` |
| `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini` | `null` / `false` | `null` / `false` |

Both catalogs carry 8 models and the same distinct `tool_mode` value set
(`["code_mode_only", null]`). Model metadata therefore still overrides
`features.code_mode*=false` for the `gpt-5.6-*` family, which is the precise
condition the clone exists for (#285). Unchanged, still required.

### (c) Disabled surfaces — **KEEP, all still present and disableable identically**

`codex features list` for every flag Cormidia sets, both versions:

| flag | 0.144.4 stage/default | 0.147.0 stage/default |
| --- | --- | --- |
| `hooks` | stable / true | stable / true |
| `code_mode` | under development / false | under development / false |
| `code_mode_host` | stable / true | stable / true |
| `code_mode_only` | under development / false | under development / false |
| `unified_exec` | stable / true | stable / true |
| `apps` | stable / true | stable / true |
| `plugins` | stable / true | stable / true |
| `in_app_browser` | stable / true | stable / true |
| `plugin_sharing` | stable / true | stable / true |

No flag Cormidia sets was removed, renamed, or changed stage or default. The
`web_search`/`tools.web_search`/`tools.view_image` keys all remain in the config
reference with the same shapes (`web_search` is still
`disabled | cached | indexed | live`; Cormidia sets `"disabled"`).

Twelve flags are new since 0.144.4; only two are worth naming:

- `view_image` appeared as a **feature** flag (stable, default true) alongside the
  pre-existing `tools.view_image` config key that Cormidia already sets to
  `false`. The live walk exercised no image path, so this is recorded, not
  claimed proven — see §7.
- `mcp_2026_07_28` (under development, default false) is the MCP protocol opt-in
  named in the upstream survey. Cormidia does not opt in.

**Scope note, deliberately not acted on:** `browser_use`,
`browser_use_external`, `browser_use_full_cdp_access`, `computer_use`,
`image_generation` and `multi_agent` are stable/default-true — but they were
*equally* default-true in 0.144.4. They are pre-existing surface, not a
regression introduced by this bump, so widening the disable list is out of scope
for a version bump. Flagged in §7 as follow-up.

### (d) `exec` defense-in-depth in the hook matcher — **KEEP**

The matcher `^(Bash|exec|apply_patch|Edit|Write|mcp__.*)$` still names `exec`,
and `normalizeCodexHookActions` still throws on it so the bridge denies the whole
call. Justification is unchanged and confirmed above: `code_mode`/`code_mode_only`
remain real flags, and `tool_mode: "code_mode_only"` still ships in the bundled
catalog, so a provider/version that ignores the disables can still surface `exec`.
`tests/unit/cf-reg-271/codex-exec-gate.test.ts` passes unmodified.

### (e) NEW — legacy approval denial shape — **ADAPT (fail-open defect, fixed)**

Not on the original checklist; found by diffing the generated protocol schemas.

`ReviewDecision`, the response type for the legacy `execCommandApproval` and
`applyPatchApproval` server requests, changed:

```
0.144.4:  … | "approved_for_session" | "denied"                        | "timed_out" | "abort"
0.147.0:  … | "approved_for_session" | { "denied": { rejection: str } } | "timed_out" | "abort"
```

`ExecCommandApprovalResponse.json` and `ApplyPatchApprovalResponse.json` are the
only two adapter-relevant schemas that changed semantically. The adapter answered
both methods with `{ decision: "denied" }` — a bare string that 0.147.0 can no
longer deserialize. **A gate DENY would have stopped arriving as a deny**, which
is an INV-002-family fail-open on the approval backstop.

Why no existing case caught it: the shared conformance walk and
`tests/fixtures/adapters/codex-double.ts` only ever exercise the **modern**
`item/*/requestApproval` methods. Both legacy methods were uncovered.

Fixed in `routeApproval` (`src/runtime/adapters/codex.ts`) via `legacyDenial()`,
which emits `{ denied: { rejection } }` and now carries the gate's own reason
string instead of discarding it. The modern decisions are confirmed **unchanged**
(`CommandExecutionRequestApprovalResponse` and `FileChangeRequestApprovalResponse`
are semantically identical between versions; `accept`/`decline` remain plain
strings), so the fix is scoped to the legacy pair only.

Detector deposited in the same change:
`tests/hermetic/cf-reg-335/codex-legacy-approval-denial.test.ts` (CF-REG-335). It
pins the encoder against the **installed Codex version's own generated schema**
rather than a hand-copied literal, so the next shape change fails here too.
Verified red-then-green: with the pre-fix bare `"denied"` encoder, 2 of 5 tests
fail; with the fix, 5/5 pass. Negative controls assert that the bare `"denied"`
string is rejected by the same oracle, that `{ denied: {} }` (missing the
required `rejection`) is rejected, that `"approved"` is still accepted (so the
oracle is not vacuously false), and that the struct form is **not** over-applied
to the modern `item/*` paths.

`ThreadStartParams`, `ThreadResumeParams` and `TurnStartParams` have identical

Reasoning effort is still `minimal|low|medium|high|xhigh` with no `max`
(`ReasoningEffort` is an unconstrained non-empty string in the schema in *both*
versions, so the ceiling is Cormidia policy, not protocol) — `mapCodexEffort`'s
throw-on-`max` stays correct.

## 7. Evaluated, not done

### Granular `approval_policy` — evaluated, **deliberately not adopted here**

`AskForApproval` accepts a struct alternative to the three-value string:

```
{ granular = { sandbox_approval: bool, rules: bool, mcp_elicitations: bool,
               request_permissions: bool = false, skill_approval: bool = false } }
```

Two findings:

1. **It is not new in 0.147.0.** The 0.144.4 schema carries the identical
   `GranularAskForApproval` variant. The upstream survey's framing of it as a
   0.145–0.147 addition is inaccurate; it predates our current pin.
2. It is an *approval-routing* selector — which categories raise an approval
   request — not a replacement for the hook bridge, which exists because
   auto-approved calls never raise an approval request at all. Adopting it could
   plausibly let `sandbox_approval`/`rules` be tuned so fewer calls bypass the
   approval channel, reducing reliance on the bridge.

Recorded as follow-up, **not** attempted here: per the issue's own instruction, a
change to approval routing is a gate-semantics change and must not ride along
with a version bump. It needs its own change with its own L2 cases and its own
live walk. Any such work must preserve enforcement semantics exactly — the
composed gate stays the enforcement, and `permission-mode.ts` keeps bypass modes
unrepresentable.

### Other follow-ups

- **Default-on surfaces predating this pin.** `browser_use`,
  `browser_use_external`, `browser_use_full_cdp_access`, `computer_use`,
  `image_generation`, `multi_agent` are stable/default-true and are *not*
  disabled by `codexAppServerArgs()`, nor covered by the hook matcher. They were
  equally default-true in 0.144.4, so this is pre-existing exposure rather than
  bump-induced regression, and the capability matrix's "constrained surface"
  caveat already scopes the gate claim. Worth a dedicated issue: decide per
  surface whether to disable it or to prove it gateable.
- **`features.view_image`** (new, stable, default true) coexists with the
  `tools.view_image=false` key Cormidia already sets. Whether the feature flag
  can re-enable the tool independently of the `tools.*` key was not probed; the
  live walk exercised no image path. Not claimed proven either way.
