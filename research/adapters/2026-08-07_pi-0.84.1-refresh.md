## 1. SDK surface diffs, and what each one cost us

### 1.1 `AuthStorage` + `ModelRegistry.create()` → one async `ModelRuntime` (breaking)

The largest break. In 0.80.7 the adapter built two objects eagerly in its
constructor and handed both to `createAgentSession`:

```ts
authStorage:   AuthStorage.create(agentDir/auth.json)
modelRegistry: ModelRegistry.create(authStorage, agentDir/models.json)
```

In 0.84.1:

- `AuthStorage` is **no longer exported** from the package index. The class
  still exists at `core/auth-storage.ts`, but the only auth symbol the index
  re-exports is `readStoredCredential`. There is no subpath export that reaches
  it (`exports` map is `.`, `./rpc-entry`, `./client`).
- `ModelRegistry` survives but is demoted to a *synchronous compatibility
  facade* — `new ModelRegistry(runtime)`, no statics. Its `getAll()`/`find()`
  delegate to `ModelRuntime.getModels()`/`getModel()`.
- `CreateAgentSessionOptions.authStorage` and `.modelRegistry` are gone,
  replaced by a single `modelRuntime?: ModelRuntime`.
- `ModelRuntime.create(options)` is **async**, which a constructor cannot await.

Applied: `PiRuntimeOptions.authStorage` + `.modelRegistry` collapse into one
`modelRuntimeFactory?: () => Promise<ModelRuntime>`, memoized on first
`runTurn()` so the runtime is still built once per adapter instance and reused
across turns — the same lifetime the eager fields had. `resolvePiModel()` is
unchanged; it now receives `new ModelRegistry(modelRuntime)`.

Two semantics were deliberately preserved rather than re-derived:

- **File-backed credentials.** `ModelRuntime.create({ authPath })` defaults its
  credential store to the file at `authPath`, matching the old
  `AuthStorage.create(authPath)`. This is load-bearing: an OAuth refresh rotates
  the token, and an in-memory store consumes the rotation and discards it, so a
  green readiness probe would break the next live turn. `src/runtime/readiness.ts`
  keeps the same store for the same reason.
- **Offline construction.** `allowModelNetwork` defaults to `false`, so
  `create()` performs no network catalog refresh. Readiness stays token-free and
  non-billable, and `readRuntimeModelCatalog()` stays a config-time-safe read.

### 1.2 `ResourceLoader` gained two provenance accessors (breaking for doubles)

`getSystemPromptSource(): { path } | undefined` and
`getAppendSystemPromptSources(): Array<{ path }>` are new required members.
Product code is unaffected — the adapter writes `.pi/APPEND_SYSTEM.md` through
`writeMaskedWorktreeFile` and never reads the loader back — but the L1 transport
double had to implement them. It reports "no source" rather than inventing a
path.

### 1.3 `model-catalog.ts` lost its in-memory-credential trick

`readRuntimeModelCatalog("pi")` previously used
`AuthStorage.fromStorage(new InMemoryAuthStorageBackend())` so that enumerating
the roster would not create or lock `auth.json`. Both symbols are unexported in
0.84.1. Replaced with an explicit empty `CredentialStore` literal typed off the
package's own `CreateModelRuntimeOptions["credentials"]` — reads as empty,
refuses to write. No new dependency: the type is reached through the
coding-agent package, never by importing transitive `@earendil-works/pi-ai`.

### 1.4 Surfaces checked and found unchanged

Verified against the 0.84.1 typings, so the adapter's existing handling stands:

- `AgentSession`: `prompt`, `abort`, `dispose`, `subscribe`, `getSessionStats`,
  `getLastAssistantText`, `sessionId`, `sessionFile` — all identical.
- Session events: `message_update.assistantMessageEvent.type === "text_delta"`,
  `turn_end`, `message_end`, and assistant `stopReason` / `errorMessage` — the
  fields `piAssistantFailure()` reads are intact, so `error_auth` vs
  `error_provider` classification is untouched.
- `SessionManager.create(cwd, sessionDir?, options?)` and
  `SessionManager.open(path, sessionDir?, cwdOverride?)` keep their arities; the
  adapter's resume call is unchanged.
- `ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>` — unchanged, so
  the fail-closed `isPiGateExtensionActive()` WeakSet check still keys off the
  exact factory identity.
- `pi.on("tool_call", …)` still receives `{ toolName, toolCallId, input }` and
  still returns `ToolCallEventResult { block?, reason?, terminate? }`. `pi-gate.ts`
  needed **no** change.
- `createBashTool(cwd, { spawnHook })` and `BashSpawnContext` unchanged, so the
  `withNonInteractiveEnv` hook still applies.

`pi-gate.ts` is byte-identical across this bump.

### 1.5 New seam, deliberately not adopted

`@earendil-works/pi-client` / `pi-protocol` / `pi-telemetry` split out as
separate packages at 0.84.1 (framed-CBOR remote sessions, reachable via the
`./client` subpath export). Cormidia continues to use the in-process SDK, which
the docs still present as the recommended path for TS orchestrators. Recorded as
a future seam, not a change.

## 2. Capability tier re-checks

Both tiers below were re-checked because the bump could have moved them. **Neither
is changed in this PR.** Each is reported as evidence for the owner, per
`docs/harness/adding-updating.md` §6 and the matrix/profile rule that a tier move
lands in the change that moves it.

### 2.1 Thinking levels — `max` stays refused

Upstream now types `ThinkingLevel = "off" | "minimal" | "low" | "medium" |
"high" | "xhigh" | "max"` (`@earendil-works/pi-agent-core`), and per-model
support is declared by `thinkingLevelMap?: Partial<Record<ModelThinkingLevel,
string | null>>` on the pi-ai `Model`. Its documented semantics:

> Missing keys use provider defaults. `null` marks a level as unsupported.

So the map has three states per level, not two: **mapped**, **explicitly
unsupported** (`null`), and **absent** (falls back to a provider default). A
model with no map at all supports nothing explicitly and defaults everything.

Measured over the shipped 0.84.1 catalog — `max` is thoroughly non-uniform:

Counts below are over models with `reasoning: true` in the shipped catalog.
"with a map" = declares a `thinkingLevelMap` at all; the remainder default every
level. `max` mapped / `max` explicitly `null` are the two decided states — any
shortfall between them and "with a map" is a model whose map simply omits `max`.

| Provider | reasoning models | with a map | `max` mapped | `max` explicitly `null` |
| --- | --- | --- | --- | --- |
| `anthropic` | 13 | 7 | 7 | 0 |
| `openai` | 26 | 26 | 3 | 23 |
| `google` | 22 | 15 | 0 | 0 |
| `xai` | 3 | 1 | 0 | 1 |
| `deepseek` | 2 | 2 | 2 | 0 |
| `amazon-bedrock` | 85 | 42 | 37 | 0 |
| `openrouter` | 247 | 53 | 29 | 4 |
| `opencode` | 59 | 41 | 15 | 20 |
| `github-copilot` | 29 | 20 | 10 | 7 |
| `cloudflare-ai-gateway` | 33 | 22 | 10 | 12 |
| `vercel-ai-gateway` | 148 | 21 | 8 | 0 |

Representative rows, verbatim from the catalog:

```
anthropic/claude-opus-5       {"xhigh":"xhigh","max":"max"}
anthropic/claude-sonnet-4-6   {"max":"max"}
anthropic/claude-haiku-4-5    (no thinkingLevelMap at all)
openai/gpt-5.4                {"off":"none","minimal":null,"low":"low","medium":"medium","high":"high","xhigh":"xhigh","max":null}
openai/gpt-5.6-sol            {"off":"none","minimal":null,"low":"low","medium":"medium","high":"high","xhigh":"xhigh","max":"max"}
xai/grok-4.5                  {"off":null,"minimal":null,"low":"low","medium":"medium","high":"high","xhigh":null,"max":null}
google/gemini-3.1-pro-preview {"off":null,"minimal":null,"low":"LOW","medium":null,"high":"HIGH"}
```

Read plainly: the whole OpenAI `gpt-5`–`gpt-5.5` line and every `o*` model mark
`max` **explicitly unsupported**; only the three `gpt-5.6-*` models map it. On
Anthropic, `max` is mapped on the newer models and simply absent on Haiku 4.5 and
the 4-5 generation. So "pi supports `max`" is false as a harness-level statement;
it is true only per (provider, model), and the holes are real.

**Decision: the unconditional throw stays.** `mapPiThinkingLevel()` still throws
on `max`, unchanged. Two reasons beyond the standing no-alias rule:

1. The refusal is not actually adapter-local. `src/runtime/assignment.ts:70`
   enforces `effort === "max" && harness !== "claude"` → throw, for **all**
   non-Claude harnesses. Admitting `max` on pi means editing that shared rule,
   which is a cross-adapter contract change, not an adapter fix.
2. A per-model capability cannot be expressed by Cormidia's `Effort` axis today.
   `Effort` is a property of an *assignment*; `thinkingLevelMap` is a property of
   a *model*. Honouring `max` correctly would need the assignment validator to
   consult the resolved model's map and refuse the holes — otherwise
   `effort: "max"` on `anthropic/claude-haiku-4-5` silently becomes a provider
   default, which is exactly the aliasing the rule forbids.

**Owner decision owed** (not taken here): whether to admit `max` on pi for the
specific (provider, model) pairs that map it, gated on a per-model capability
check. Until ratified, `max` on pi is a hard error, which is the honest tier.

### 2.2 Intra-turn fan-out — still `unsupported`, and now positively verified

Re-checked because the epic flagged a possible new subagent surface. There is
none in 0.84.1:

- Exhaustive `.d.ts` search across **all seven** shipped packages
  (`pi-coding-agent`, `pi-agent-core`, `pi-ai`, `pi-client`, `pi-protocol`,
  `pi-telemetry`, `pi-tui`) for `subagent|sub-agent|fan.?out|spawnAgent|swarm|
  delegate` returns **zero** hits.
- The built-in tool union is closed and contains no task/agent tool:
  `ToolName = "read" | "bash" | "edit" | "write" | "grep" | "find" | "ls"`.
- The extension event union (`ExtensionEvent`) has no subagent lifecycle event,
  and `ToolCallEventBase` carries only `{ type, toolCallId }` + `toolName` +
  `input` — no agent attribution field.

`intra_turn_fanout: "unsupported"` in `src/runtime/capabilities.ts` therefore
remains correct and is **not** touched. `pi-gate.ts`'s `isSubagentToolCallEvent()`
defensive probe is retained: it costs nothing, and it is what would surface an
undocumented attribution field if one appeared. The `piArtifacts()` degradation
note remains the proof for the `unsupported` tier, per §5's probe table.

No capability-matrix row moved, so no matrix edit is owed by this change.

certification is per harness surface, not per model, and publishing a model in
the roster assigns it to no role.

## 4. Bands moved

`src/runtime/harness-support.ts`:

- `pi.testedWith`: `0.80.7` → **`0.84.1`** (the exact version the walk above ran
  against).
- `pi.testedEvidence`: → this file.
- `pi.floor`: **unchanged at `0.80.7`**, deliberately. The floor is a claim about
  the oldest interface the adapter genuinely speaks, not a copy of the pin;
  raising it to match would refuse operators who have not upgraded, which is the
  exact failure bands exist to prevent. Lowering it to the true oldest interface
  is per-adapter research owed with #224.

Supply-chain allowlist: `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude` moves
to exact `@0.84.1` entries (pi ships ~3 releases/week, so the pin is always
younger than the default minimum release age). The stale `0.80.7` allowances are
dropped rather than kept as a range, so a later upload is never admitted
silently; `pi-client`, `pi-protocol`, and `pi-telemetry` are new package names at
the same single pinned version.

## 5. Standing warning, restated

The author's release notes explicitly tell SDK/RPC/extension users to re-read the
docs on upgrade, and this bump justified that: four releases moved the auth/model
construction path, unexported two classes, and added required `ResourceLoader`
members. Treat every future pi bump as breaking until the typings say otherwise —
re-read the docs first, re-run this walk, and re-check both tiers above.
