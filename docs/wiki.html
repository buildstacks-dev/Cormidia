TypeScript · one package · three layers

Operon / a standing org of AI agents that ships software

A reusable org runtime: Planner, Builder, Reviewer, SRE, Support, and Marketing agents that develop and operate a product through a private GitHub repo — with a human gating only the critical operations. It is a library, not an app: pointed at a target repo by config, it never contains app code.

In molecular biology, an operon is a cluster of genes transcribed as a single unit under one operator. The same shape as this system: many role-agents expressed as one functional org, under a single critical-ops gate. The name is the architecture.

Orientation

What you are looking at

Operon coordinates a team of language-model agents the way a small engineering org coordinates people. Work arrives as GitHub issues; a Planner shapes them, a Builder implements, a deliberately separate Reviewer checks the work, and mechanical quality gates run between every step. Nothing merges on an agent's say-so alone — side effects are git and GitHub artifacts, and a human approves the irreversible ones.

The codebase is a single TypeScript package. Its most important property is a strict layering you can rely on while reading:

The one non-negotiable

Imports flow one way only: src/org → src/loop → src/runtime. The runtime layer imports nothing above it. This is what keeps the build loop extractable, and it is the single rule to hold in your head while navigating — if you ever see src/loop importing src/org, that is a bug, not a pattern.

Orientation

The three-layer stack

Each layer has one job and depends only on the layer beneath it. Read them bottom-up — the runtime contract is the vocabulary the two upper layers speak.

src/orgthe standing org — scheduler, apps & roles, approvals, context, memory, scorecards, retro
▲ imports
src/loopthe build loop — pass pipelines, briefs, quality gates, typed verdicts, the ticket state machine, GitHub ops
▲ imports
src/runtimeprovider-neutral contract — the Runtime interface, the critical-ops gate, telemetry, the L1/L2/L3 runlog, three adapters

Dependencies flow downward only. Extraction of the loop is a mechanical move, not a rewrite.

A fourth surface sits outside src/: the human-ratified config — roles.yaml, apps.yaml, pipelines.yaml, TASTE.md, and prompts/**. These encode the org chart, the build protocol, and the constitution as diffable text. The org's own gate treats agent writes to them as critical operations.

Runtime layer

The Runtime contract

src/runtime/types.ts is the only surface the upper layers see. It defines a single Runtime interface — runTurn(request, hooks) — so no code above ever touches a provider SDK. Swapping a role's model is a config change, not a rewrite.

Runtime layer

The critical-ops gate

Agents work autonomously — including merging reviewed work to main. The gate exists to stop the small set of operations a human must own. It classifies every tool action; a critical verdict is denied and escalated to the approval queue, a routine one is allowed. A denied op doesn't resume in place — the human's approval writes a single-use grant that a later dispatcher tick retries (Dispatch & approvals).

The classifier is deliberately over-broad — it fails closed. The critical classes cover production deploys, destructive or irreversible operations, DNS and domains, external publishing, secrets and credentials, writes to the org's own protocol surfaces, the approval-grant store, self-merge / self-approve, and outbound network exfiltration.

The invariant that makes it trustworthy

The gate must see every tool action, including those issued from inside a subagent. This is an adapter-level conformance requirement: every adapter passes the same suite, in which a subagent-issued critical op is caught identically. An all-pi org gets the same guarantee as an all-Claude one — that is why the guarantee lives in the contract, not in one adapter.

Runtime layer

Runlog — if it executes, its logs exist

Every pass leaves a three-tier run record under ~/.operon/<org>/runs/<app>/<runId>/. The tiers separate what is safe to export from what stays local.

L1 · envelope.jsonThe summaryIds, status, timings, token/cost rollups, gate results, verdict summary. Redacted previews only — references L3, never inlines it. Written atomically (temp + rename).
L2 · events.jsonlThe timelineAppend-only taxonomy: run.*, pass.*, gate.*, ticket.transition, verdict.recorded, escalation.raised. Subagent spans nest by parent_span_id. Every field scrubbed.
L3 · brief / output / sessionThe forensicsVerbatim, unredacted, local-only: the assembled brief, the raw output, the full session log. Pruned on a retention window.

Anomaly detectors (long single-turn runs, cold cache, and more) read L1/L2 after the fact.

Loop layer · the center of gravity

The build loop

This is where a GitHub issue becomes a squash-merged PR. It is a pipeline of versioned passes, not one opaque prompt — planning is a pipeline, Builder and Reviewer passes each get an assembled brief, and mechanical gates run between passes and twice at ship. No side effect keys off agent prose.

ModuleResponsibility
loop.tsThe ticket state machine — label transitions, review cycles, remediation, squash-merge, merge authorization. The heart of the layer.
driver.tsThe phase loop that advances an item until a terminal state, with a hard guard against runaway.
pipeline.tsThe pass executor — fresh session per pass, brief + template as task, parallel groups, and the full run record written for every pass.
pipelines.tsLoads & validates pipelines.yaml; selects which passes run for a tier / trigger.
brief.tsDeterministic, token-budgeted brief assembly — ticket + spec + contract + findings + history + memory + repo conventions, in a fixed order.
qgates.tsThe mechanical gates: setup, tests, lint, security scan, completeness, review-freshness. See below.
verdicts.tsTyped verdicts (contract / build / review) with a lenient parser and a one-shot reformat retry.
github.tsAll GitHub operations — issues, PRs, reviews, labels, squash-merge — plus the HMAC self-approval marker.

Loop layer

The ticket state machine

A ticket is its GitHub label. The loop moves the label after the artifacts it announces, so a crash never leaves a lie on the board. Every path is bounded — it terminates in merged, returned, or blocked, never a silent spin.

op:ready→ building→ gates→ reviewing→ shipping→ merged
op:returned — engineering dead-end or review that won't converge (bounded by the cycle cap) returns to the Planner. op:blocked — a safety escalation waiting on a human. The build loop itself only ever writes op:returned.

Review cycles > 3 → returned · gate remediation is capped · a stale approval never merges and never spins.

Merge authorization

A merge requires an independent reviewer approval matching the exact reviewed commit. In a single-token setup where builder and reviewer share one GitHub identity, GitHub rejects the self-approval — so the loop falls back to an HMAC-signed marker verified against OPERON_SELF_APPROVAL_SECRET. There is no static, forgeable bypass. Set that secret for autonomous single-maintainer operation.

Loop layer

Quality gates

The mechanical layer between passes — pure subprocess and git, no model. Gates are selected by the change's risk tier (from .operon/policy.yaml), run in order, and each returns a typed result.

GateWhat it checks
setupRuns the app's setup_command (e.g. npm ci) first, so the fresh worktree has its dependencies before tests or lint. A setup failure short-circuits the set.
testsThe configured test command; captures a bounded output tail on failure, with a distinct timeout message.
lintThe configured lint command, analogous.
securityScans changed files for the secret families from secret-patterns.ts — reports file:line, skips binaries.
completenessCriteria present and parseable, no unresolved findings, and every criterion mapped to a named test. An unmapped criterion fails — it does not warn. Checkbox state is gate output: the orchestrator renders the boxes checked when the ticket merges.
review-freshnessBranch head equals the approved commit. Always runs, regardless of tier.

Acceptance criteria are a first-class contract: binary, mapped to named tests, never summarized away. That mapping is what the completeness gate enforces.

Loop layer

Briefs & typed verdicts

Two functions keep agent prose out of control flow. Brief assembly (brief.ts) turns "the feature doc plus the relevant history plus the learnings" into a deterministic, byte-reproducible, token-budgeted string — the ticket and its acceptance criteria are never summarized, even under a tight budget. Verdict parsing (verdicts.ts) turns a pass's scrappy markdown into a typed Finding[]; a parse failure gets exactly one session-resuming reformat retry, then fails loudly with an infra error code distinct from a merit failure. Adapters with native structured output skip the parser entirely.

Org layer

The standing org

The top layer runs the org over time: it decides what to run, gates the critical operations, assembles each turn's context, and closes the learning loop. It is multi-app by design but operates one live app at a time — human bandwidth is protected by construction.

Org layer

Dispatch & approvals

The autonomous host is a plain operon dispatch tick that any scheduler can call — launchd now, a systemd timer later. A tick is stateless: it derives readiness from artifacts, spawns detached turns into org-managed clones, and refreshes the monthly budget overlay (auto-pausing an app past its cap, resuming it next month under cap).

Approvals are grants, not auto-execution

A critical-op approval is an expiring, single-use, action-hashed grant for a later retry — the orchestrator never executes the operation itself. The human reviews the queue one item at a time; every decision is a persisted audit trail. There is one app-tagged queue, never one per app.

Org layer

Context, memory, and the retro loop

Knowledge lives in three tiers. The constitution (TASTE.md) is slow-moving and human-gated. Skills are curated distillations of recurring lessons. Working memory is per-role OKF bundles the agents write freely at end of turn — vendor-neutral markdown that survives model and runtime swaps.

A weekly retro reads the forward scorecards — Reviewer escaped-bugs, Planner rework rate, Builder review cycles — and turns them into memory updates, skill promotions, and proposed constitution changes (which stay human-gated). Wrong lessons are deleted, not hedged. Context assembly loads the role bundle plus the current app's bundle only, in a fixed order so the prompt cache stays stable.

Org layer

The learning loop

Governed self-improvement over the run record, built as a funnel: capture projects gate outcomes, verdicts, and human observations into learning events; episodes & capsules assemble them into rebuildable episode records and replayable build capsules; experiments are declared before results and evaluated offline (paired replay from trusted fixtures, learning-budget-capped); activation is manual and governed — fail-closed review, journaled publish, per-turn pinned resolve, disable and rollback; and a human-started canary trials a published change live with episode-sticky assignment. M6 is complete and live: scheduled distillation uses deterministic zero-token prechecks, ordinary metered provider turns, independent review, policy caps, and report-only compaction.

The implementation is src/org/learning/; captured state lives under the state home's learning/** (events, episodes, capsules, fingerprints, resolve records), governed artifacts under the committed org home's learning/** (experiments, interventions, eval fixtures, reviews, the active bundle + manifest). The human window is operon learn — report/inspect, review/publish/resolve/disable/rollback, experiment declare/run, canary start/promote/stop. Full design: docs/learning-loop/.

Prerequisites

Node ≥ 26 and the pinned pnpm. From a source checkout run pnpm install, then pnpm link:local; the source-backed operon command and $operon skill see subsequent source edits without an update or rebuild. Start with operon org init <path> --name <name> and operon doctor. Live commands additionally need provider auth; the GitHub e2e needs gh auth plus GH_SANDBOX_REPO; the loop's merge needs OPERON_SELF_APPROVAL_SECRET.

Testing & the sandboxes

pnpm test is fast and offline (571 cases). It is backed by shared fixtures — a temp org-home builder, a deterministic clock, real-git repo fixtures — and the adapter-generic conformance suite in test/conformance/, which every Runtime must pass before a role goes live on it. Live adapter turns and the disposable GitHub e2e run separately and spend real resources.

Functional proof runs against four disposable sandbox apps, not just unit tests:

SandboxIts job
alphaA well-kept Node library with tests, lint, CI, agent docs — the primary build-loop target.
betaDeliberately minimal (tests only, no CI/AGENTS.md) — proves graceful absence handling and second-app join.
gammaA deployable HTTP service with /health, /metrics, a feedback inbox, and seeded events — the SRE / Support / Marketing target.
delta"Ledgerette", a realistic zero-dep expense API with real eslint, CI, and a planted-bug backlog — the comprehensive from-scratch onboarding & loop proof.
Proven, not just claimed

The live loop took two deliberately planted bugs in delta — a timezone month-boundary error and a float-rounding artifact — from a labelled issue through contract, implementation, gates, an independent review, and a squash-merge, autonomously. Tests alone can't prove that; running the loop can.

Operate

Known limitations

Recorded honestly so you don't rediscover them as bugs:

Tool-outcome telemetry

All three adapters now emit tool_use turn events through the one shared builder (src/runtime/tool-events.ts, issue #27), so envelope.tool_counts fills and every anomaly detector can fire. The residual: Claude and pi emit pre-execution (the gate hook fires before the tool runs), so their events carry no success/duration outcome — only Codex's completed item stream reports real exit codes and timings.

Codex read bypass

Under the App Server's untrusted policy, trusted read-only commands run without an approval request, so those reads don't reach the gate. Documented in the capability matrix as a live-verified follow-up.

Glossary

org runtime
The whole system: a standing team of role-agents that develops and operates a product. A library pointed at a target repo.
pass
One versioned step in a pipeline (contract, implement, verify, fix, ship-check), run as a fresh model session.
brief
The deterministic, token-budgeted context assembled for a pass — ticket, spec, contract, findings, history, memory, repo conventions.
verdict
The typed result of a pass (contract / build / review), parsed from the turn's output; never raw prose driving control flow.
critical op
An operation the human must approve: deploys, destructive changes, DNS, publishing, secrets, protocol edits, self-merge.
grant
An expiring, single-use, action-hashed authorization for a previously-escalated critical op to be retried.
runlog
The three-tier per-pass record: L1 envelope, L2 events, L3 forensics.
tier
The risk level of a change (from policy.yaml), which selects the gate set and review dimensions.
OKF
Open Knowledge Format — the vendor-neutral markdown + YAML memory bundles agents read and update.
TASTE
The layered constitution (org values → role craft → app charter) every agent loads at bootstrap.
