## Deltas applied

### 1. Version pin → 0.3.224

`package.json` exact pin plus lockfile. `pnpm add -E` also appended nine
`minimumReleaseAgeExclude` entries to `pnpm-workspace.yaml` (the SDK plus its
eight platform packages), because 0.3.224 was published ~8 hours before this
bump and sits inside the repo's `minimumReleaseAge` cooldown. That is a
deliberate, recorded relaxation of a supply-chain gate for these exact
name@version pairs, following the precedent already in that file for
`@earendil-works/pi-*@0.80.7`. It is worth a reviewer's eye: we are pinning a
same-day upload.

### 2. `strictMcpConfig: true` — the hermeticity delta

This is the only behavioral change to `src/runtime/adapters/claude.ts`.

`settingSources: []` and MCP discovery are **disjoint paths**. The SDK's own
`strictMcpConfig` doc names what is otherwise consulted: "project `.mcp.json`,
user settings, plugins, and on-disk agent frontmatter — including subagent
frontmatter MCP". `settingSources` scopes itself to the user/project/local
*settings* layer and CLAUDE.md. So the adapter's standing claim that
`settingSources: []` alone "keeps the turn hermetic" was **narrower than it
read**: an app repository checked out into `req.workdir` could contribute MCP
servers to an org turn through its own `.mcp.json`.

`strictMcpConfig: true` closes that. It restricts MCP to servers a caller passes
explicitly via `mcpServers`, which no caller in this repo does today, so the
change is a pure tightening with no functional effect on any existing path.
Both halves of the pair are now pinned offline in
`tests/fixtures/adapters/claude-double.test.ts`, including a **negative control**
that seeds the exact weakening a careless caller would write
(`baseOptions: { settingSources: [...], strictMcpConfig: false }`) and asserts
the adapter's own keys still win.

## Deltas deliberately skipped

### `--bare` — CLI-flag-only, no SDK surface; and it would break our auth

Not adopted. Two independent reasons, either sufficient:

1. **It is not an SDK option.** The 0.3.224 `Options` type has 60 keys and none
   is `bare`; the string `--bare` appears **zero** times in the shipped
   `sdk.mjs`. It is reachable only as a raw CLI argument, and only through the
   `extraArgs` escape hatch — which is an arbitrary-flag passthrough, not a
   supported option surface. #335's instruction for this case is to record it
   honestly and change nothing.
2. **Bare mode is incompatible with how this org authenticates.** The headless
   doc states that in bare mode Claude Code "never reads OAuth credentials or
   the system keychain" and requires `ANTHROPIC_API_KEY`. The adapter's
   `protectedHome` path exists precisely to serve macOS Keychain-backed operator
   authentication, and the certification run below used the operator's
   first-party claude.ai login. Adopting `--bare` would therefore not be a
   hermeticity refinement; it would be an authentication-model change, which is
   a material product decision and not this ticket's to make.

The `research/2026-08-06` survey's recommendation to "re-express hermeticity on
`--bare` when we bump the pin" is therefore **superseded**: the parts of bare
mode reachable from the SDK are `settingSources: []` (already held) plus
`strictMcpConfig` (adopted here). If bare mode becomes the default for `-p` as
the docs forecast, the auth question above becomes a real decision that needs a
human — it is not resolved by this record.

**Residual, disclosed:** bare mode also skips auto-discovery of hooks, skills,
plugins, and auto memory. The SDK exposes `skills` and `plugins` options, and
the `skills` doc is explicit that omitting it is "**not** 'skills off'". This
refresh did not change those, so the honest statement of our hermeticity is now
the one written into the adapter header: settings/CLAUDE.md and MCP are closed;
filesystem skill and plugin discovery is not independently pinned. Narrowing
that further is a follow-up, not a silent extension of this change.

### `thinking: ThinkingConfig` — nothing to migrate

`maxThinkingTokens` is indeed deprecated in 0.3.224 in favor of
`thinking?: ThinkingConfig`. **Our adapter never set `maxThinkingTokens`**
(`grep` over `src/` and `tests/`: the only `thinking`-shaped code is pi's
unrelated `thinkingLevel`). There is nothing to migrate, and adopting `thinking`
speculatively would add a knob no role asks for. Thinking depth continues to be
driven by `effort`, which the SDK documents as working with adaptive thinking.

Skipped without change; re-check if a role ever needs an explicit thinking budget.

  not advisory, and the gate path was observed (two normalized `bash` actions

## Collateral found while landing this

The bump surfaced two problems that were **latent, not introduced**, in
`tests/hermetic/cf-release-evidence/release-evidence.test.ts`:

1. **The release fixture omitted an install input.** `writeRepositoryFixture()`
   reproduces the candidate repo for the release lane's
   `pnpm install --frozen-lockfile`, copying `package.json`, `pnpm-lock.yaml`,
   `.gitignore`, and `vitest.config.ts` — but not `pnpm-workspace.yaml`, which is
   this repo's pnpm *config* (supply-chain policy, `allowBuilds`) rather than a
   workspace declaration. The fixture's lockfile and its policy therefore
   disagreed, and any dependency published inside the `minimumReleaseAge` window
   failed the fixture's own install rather than the candidate. It passed before
   only because no pinned dependency happened to be that fresh. Fixed by copying
   the file; the fixture is now a faithful reproduction.
2. **Three install-bound cases outgrew their timeouts.** The Claude platform
   package grew 221 MB → 265 MB (+20%) between 0.3.201 and 0.3.224, and these
   cases drive several real `pnpm install --verify-store-integrity` runs each.
   The heaviest was already at ~48s against a 90s budget and landed at ~83s —
   flaky, not failing-for-cause. Budgets raised to 240s. No assertion was
   changed, added, or removed: this is wall clock for I/O, not a gate.
