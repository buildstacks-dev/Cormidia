# Operon Learning Loop — Consolidated Design Feedback

> **Superseded** by the ratified v0.8 suite (2026-07-11); kept as historical record.

**Status:** Redesign brief, 2026-07-10.  
**Purpose:** Self-contained handoff for a fresh session to redesign the learning-loop documents before a separate implementation session begins.  
**Assumption:** The work in `docs/proportionality-review.md` is fully implemented and becomes the evidence and episode substrate on which this design builds.

## Overall assessment

With the proportionality review fully implemented, Operon will have the right evidence substrate: durable episode state, honest telemetry, bounded retries, proportional planning, release outcomes, and a repeatable benchmark. That materially strengthens the learning-loop proposal.

My verdict: **approve the architectural direction, but revise the design before implementation.** As written, V1 is a strong governed change-management loop:

```text
evidence → candidate → review → approval → publication → exposure → report/rollback
```

It is not yet a defensible empirical learning loop:

```text
baseline → isolated intervention → comparable outcomes
→ measured effect → promote or reject
```

In other words, it can safely introduce plausible improvements, but cannot yet prove that a specific change caused the agents to improve.

| Area | Assessment |
| --- | --- |
| Evidence substrate after proportionality | Strong |
| Governance and containment | Strong |
| Artifact routing | Strong |
| Causal measurement | Incomplete |
| Specification consistency | Needs revision |
| Implementation milestones | Over-bundled |

### What the design gets right

Several decisions are excellent and should be preserved:

- Learning is correctly applied to the entire harness—not just memory. Evidence can become an OKF concept, skill, protocol proposal, gate, test, or engineering ticket. See [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:19).
- Run repair and durable learning are separate trust regimes. A failed run is repaired immediately; changing future behavior goes through the governed loop.
- Agents stop writing directly into active future context. Moving from “agent writes memory” to “agent emits a candidate” is the most important safety correction in the design. See [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:280).
- Agent self-reports are advisory and excluded from efficacy metrics, reducing reward-gaming risk.
- Cross-provider review, human-gated activation, provenance, quarantine, pinning, surgical disable, and rollback are all sound foundations.
- The “lowest-authority, narrowest useful scope” rule is exactly right.

## Required design changes

### 1. Add an executable experiment contract

The candidate schema contains evidence, destination, scope, and a proposed artifact, but it does not say how improvement will be demonstrated. The required metrics are mostly counts and pass/fail values. See [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:251) and [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:585).

Every candidate that claims improvement should carry an `ExperimentRecord` containing:

- The behavioral hypothesis.
- The eligible task/episode population.
- Control and treatment fingerprints.
- Primary outcome and expected direction.
- Quality, safety, cost, and human-attention guardrails.
- Minimum practically useful improvement.
- Observation or outcome-maturity window.
- Stop and rollback thresholds.
- Final result: `improved`, `regressed`, `inconclusive`, or `not_evaluatable`.

Human approval may authorize an unproven change, but that must remain distinct from “efficacy validated.”

### 2. Assign treatments by episode, not by turn

The proposal hashes `turnId` for canary selection. But a ticket can span Builder, Reviewer, fix, gate, and ship turns. Different turns in one workflow could therefore receive different learning bundles, contaminating both the work and the measurement. See [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:411).

After proportionality is implemented, the natural assignment unit becomes:

- Ticket or milestone for build work.
- Incident episode for SRE work.
- Feedback thread for Support.
- Campaign or release for Marketing.

Assignment should be sticky across all roles, retries, and passes in that episode. The event schema consequently needs `episode_id`, stage, risk tier, pipeline, pass, and release disposition—not only `turn_id` and `run_id`.

### 3. Specify the eval and replay system

The design names held-in and held-out evaluation, but it does not define an eval schema, runner, grader, or reproducibility capsule. See [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:316).

Before live canaries, define:

- A pinned task input and seed repository commit.
- Operon, org, app, prompt, pipeline, gate, skill, and bundle revisions.
- Provider, model, effort, budget, and tool configuration.
- A held-in reproduction of the observed failure.
- Hidden held-out regression cases unavailable to the acting agent.
- Multiple paired trials where model nondeterminism matters.
- Deterministic or independently reviewed scoring.

The post-proportionality bootstrap benchmark is a good first global eval, but it is not sufficient as the general learning suite.

### 4. Track every harness intervention, not only OKF

The design correctly says improvements may affect skills, prompts, protocols, gates, models, or code. But versioning, canaries, measurement, disable, and rollback are largely specified only for OKF bundles.

Introduce a common `InterventionRecord` linking:

```text
candidate
→ reviewed content
→ final PR/commit/config change
→ activation time
→ affected episodes
→ experiment
→ outcome
→ rollback
```

Not every change should use a live canary. Security, permissions, deployment, and destructive-operation changes should generally use sandbox, replay, shadow, or explicitly bounded trials. But every destination needs activation and outcome lineage.

### 5. Fix the immediate safety inconsistencies

Several specification details are blockers:

- `candidate`, `provisional`, and `active` currently map to top-level `status: active (resolvable)`. That could make an unreviewed candidate load into future turns. See [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:154). Candidates must live outside active bundles; the resolver should require `loop.status === active`.
- T2/T3 “concepts” risk becoming a memory-based bypass around human-ratified protocols. OKF should hold bounded facts and procedures. Permissions, security posture, deployment, tools, gates, and constitutional behavior should remain proposal/code/config changes.
- Human approval must bind immutable candidate bytes, verdict hash, destination, tier, scope, base commit, and final diff. A deterministic publisher—not the distiller or reviewer—should perform one atomic, idempotent publish transaction.
- Protect `learning/policy.yaml`, eval definitions, reviewer records, and the rejection ledger. The current gate proposal protects only bundles and manifests.
- Provisional TTL expiry must be enforced by the resolver, not left to a report-only compaction process.
- T3’s proposed 5% canary must not mean random live exposure for permissions, deployment, or security changes.

### 6. Correct resolver and storage semantics

The resolver loads broad org concepts first “until the budget is reached,” which can starve the narrower app-role scope that is supposed to have higher precedence. “Scope budget shares” are referenced but not defined. See [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:460).

Resolve conflicts before budgeting, then reserve capacity or prioritize narrower scopes during eviction. Bundle-size violations should be caught before activation; one oversized protected concept should not brick all future turns.

There are also two concrete integration defects:

- The spec says the org home is the Operon source checkout, conflicting with the ratified package/org/state/app separation in [PURPOSE.md](/Users/bikram/Build/Operon/docs/PURPOSE.md:195).
- The spec says the existing OKF parser supports the new `loop` block unchanged, but the current validator reconstructs only known fields and drops extensions in [memory.ts](/Users/bikram/Build/Operon/src/org/memory.ts:187).

### 7. Keep the learning loop itself proportional

V1 requires human approval for every publication—including ordinary internal issues and proposal drafts. That risks recreating the exact human-attention failure that proportionality is meant to solve.

Human approval should gate:

- Activation into future context.
- High-authority or critical changes.
- Promotion and live experimentation.

Opening a deduplicated internal ticket or an unmerged proposal should usually remain routine. One human decision should authorize one content-hashed publish transaction, not trigger several file-level approvals.

The current V1 milestone also combines capture, migration, two new agents, six destinations, approval integration, manifests, resolution, metrics, canaries, rollback, and compaction. That is too much for one proving milestone.

### 8. Define a complete human review and correction workflow

The design intends to accept human input, but it does not yet define a usable end-to-end workflow. Capture names explicit human corrections in [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:178), the event schema includes `human_correction` in [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:193), and the CLI lists `operon learn emit` in [learning-loop-spec.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-spec.md:543). However, the submission mechanism remains an open question in [learning-loop-design.md](/Users/bikram/Build/Operon/docs/learning-loop/learning-loop-design.md:447).

The missing capability is a traceable human-review path tied to a durable episode. A human reviewing a ticket, incident, support thread, campaign, or other completed task must be able to:

- Inspect the complete episode, including its turns, runs, artifacts, gates, decisions, configuration fingerprint, and outcome.
- Record one or more observations against that episode.
- Identify the affected role, stage, or artifact when known.
- Attach immutable evidence references.
- Track each observation through classification, candidate creation, evaluation, activation, rejection, or deferral.

The input contract must keep three fields separate:

1. **Observation:** What the human directly saw. This is trusted human-origin evidence.
2. **Cause hypothesis:** Why the human thinks it happened. This remains a hypothesis even when supplied by a human.
3. **Suggested intervention:** What the human thinks might improve it. This still requires review and evaluation.

A minimum CLI workflow could be:

```text
operon learn inspect <episode-id>
operon learn emit --episode <episode-id>
operon learn show <event-or-candidate-id>
```

`operon learn emit` may be interactive or accept a structured Markdown/JSON artifact. Its resulting event should include the episode id, author identity, affected app/role, observation, optional cause and intervention, evidence hashes or durable references, and the system fingerprint under which the episode ran.

Two manual lanes are required:

- **Normal correction:** enters the standard capture → distill → review → evaluate → activate/reject workflow.
- **Urgent provisional instruction:** a human may add explicitly unverified quarantined context with a hard TTL through `operon learn provisional`; it must never silently promote.

Human provenance should increase trust in the observation, not make the proposed cause or intervention automatically correct. Human-originated suggestions still pass through the experiment and outcome-measurement contract. A V1 acceptance case should start with a human reviewing a completed episode, submitting multiple observations, and tracing each one to a distinct final disposition.

### 9. Make the episode the learning and experimental unit

A **turn** is one role-agent's contribution. An **episode** is the complete end-to-end task whose outcome the organization is responsible for.

For example, one build episode may contain:

```text
Episode: deliver ticket #42
├── Planner turn
├── Builder contract turn
├── Builder implementation turn
├── Reviewer turn
├── Builder fix turn
├── quality gates
└── merge and release disposition
```

Turn-level records remain essential for diagnosis: they show which role made a decision, repeated work, missed context, raised an escalation, or produced a finding. The episode supplies the meaningful outcome: whether the task completed, shipped, stayed within budget, required rework or human attention, and later produced an escaped defect or incident.

The governing rule should be:

> Learning evidence may originate at the turn level, but treatment assignment and outcome measurement normally happen at the episode level.

Every episode should durably contain or reference:

- The original task, ticket, incident, feedback thread, campaign, or event.
- Stage, risk tier, app, participating roles, and release disposition.
- The system fingerprint under which it ran.
- All turns, retries, gates, approvals, artifacts, and side effects.
- Immediate outcome metrics and later-maturing outcomes.
- Human observations and their eventual dispositions.

Canary assignment must be sticky across every eligible turn and retry in the episode. Natural episode boundaries are a ticket or milestone for build work, an incident for SRE, a feedback thread for Support, and a campaign or release for Marketing.

### 10. Add executable experiment contracts

An executable experiment contract is a machine-readable answer to:

> What change is being tested, on which episodes, compared with what baseline, how will success and harm be measured, and which result causes promotion, extension, rejection, or rollback?

The contract is declared before results are observed. It must distinguish a human-authorized change from an efficacy-validated change.

#### Example A — Builder maps acceptance criteria to tests

```yaml
experiment: builder-test-mapping
unit: build-episode

hypothesis:
  Adding the test-mapping skill will reduce review rework without
  materially increasing cost.

control:
  builder_bundle: v12

treatment:
  builder_bundle: v13
  added_concept: map-acceptance-criteria-to-tests

evaluation:
  episodes: evals/builder/standard-tickets
  primary_metric: average_review_cycles
  expected_change: at_least_20_percent_lower

guardrails:
  merge_success_rate: must_not_decrease
  gate_pass_rate: must_not_decrease
  average_cost: no_more_than_10_percent_higher

decision:
  promote_if: primary_metric_improves_and_all_guardrails_pass
  otherwise: reject_extend_or_revise
```

#### Example B — Planner uses proportional decomposition

```yaml
experiment: proportional-bootstrap-planning
unit: planning-episode

hypothesis:
  Stage-aware planning will produce smaller independently shippable
  bootstrap milestones without losing acceptance coverage.

control:
  planner_prompt: current

treatment:
  planner_prompt: proportional-v2

evaluation:
  episodes:
    - personal-website-bootstrap
    - small-api-bootstrap
    - internal-dashboard-bootstrap

primary_outcomes:
  bootstrap_ticket_count: between_1_and_3
  first_milestone_is_shippable: true

guardrails:
  acceptance_criteria_coverage: at_least_control
  dependency_errors: zero
  release_disposition_present: true

decision:
  promote_if: all_episodes_pass
```

#### Example C — Support avoids unsupported claims

```yaml
experiment: support-source-grounding
unit: support-feedback-episode

hypothesis:
  The source-grounding skill will prevent fabricated replies and reduce
  human editing.

control:
  support_bundle: v7

treatment:
  support_bundle: v8
  added_skill: source-grounded-support

evaluation:
  episodes:
    - feedback-with-complete-payload
    - feedback-with-missing-payload
    - conflicting-customer-reports
    - hostile-untrusted-feedback

primary_outcomes:
  unsupported_claims: zero
  average_human_edit_distance: lower_than_control

guardrails:
  valid_feedback_not_ignored: true
  response_latency: no_more_than_20_percent_higher

decision:
  rollback_immediately_if: unsupported_claims_above_zero
  promote_if: all_safety_checks_pass_and_edit_distance_improves
```

These examples are illustrative policy values, not universal thresholds. The redesign must define the schema, validator, eligible episode set, outcome maturity, grader, and decision semantics explicitly.

### 11. Define the eval and replay system in three layers

Replay does not mean reproducing the old transcript or forcing a model to emit identical responses. It means recreating equivalent starting conditions and asking the current and candidate systems to attempt the task again. Model nondeterminism may require multiple paired trials.

The learning system should have three evaluation layers:

| Layer | Purpose | Real model turns | Typical trigger |
| --- | --- | --- | --- |
| Fast deterministic tests | Prove schemas, projection, resolution, pinning, approval binding, gates, disable, and rollback | No | Every implementation PR |
| Offline behavioral replay | Compare stable and candidate behavior in isolated episode fixtures | Yes | Before candidate activation or on an explicit scheduled/manual eval |
| Live episode canary | Verify that an offline improvement survives genuine new work | Yes, but performs useful work | Only after replay succeeds and the trial is safe |

The intended asynchronous flow is:

```text
Live episodes continue operating
        ↓
Evidence and human observations accumulate
        ↓
Candidate intervention is proposed
        ↓
Deterministic checks and targeted behavioral eval
        ↓
Paired offline episode replay: stable versus candidate
        ↓
Human-started sticky episode canary when safe
        ↓
Promote, extend, reject, or rollback
```

True held-out behavioral cases must remain verifier-only. Visible tests in the app or org repository are valuable regression tests, but they are not held out if the acting agent can read and optimize directly against their expected answers.

### 12. Make `ReplayCapsule` a first-class Operon contract

The system should design for replay while an episode is running rather than attempting to reconstruct everything from logs afterward. Logs describe what happened; a replay capsule contains what is necessary to safely attempt the task again.

```text
episode logs
+ original inputs
+ repository/data snapshot
+ system fingerprint
+ sandbox and side-effect policy
+ expected outcome and grader
= ReplayCapsule
```

#### Operon core responsibilities

Operon should provide the deterministic recording and reproduction substrate:

- Durable `EpisodeRecord` and lifecycle.
- Original task/event input and immutable evidence references.
- Seed repository commit, required fixtures, and artifact references.
- `SystemFingerprint`: Operon, org, app, model, role, prompt, pipeline, skill, gate, learning-bundle, budget, permission, and environment versions.
- Turn/run lineage, gates, approvals, usage, costs, and final release disposition.
- External side-effect ledger and a policy for replacing real effects with fakes, sandboxes, staging, or shadow execution.
- Capsule completeness validation, sandbox creation, artifact restoration, run orchestration, and deterministic grading.

#### Learning-loop responsibilities

The learning loop should decide what deserves evaluation and how to interpret it:

- Select useful episodes and convert them into sanitized eval fixtures.
- Define the behavioral hypothesis, expected outcome, primary metric, guardrails, and trusted grader.
- Construct control and treatment fingerprints.
- Execute targeted evals and paired episode replays.
- Compare outcomes and produce `improved | regressed | inconclusive | not_evaluatable`.
- Recommend promotion, extension, rejection, disable, or rollback.

The boundary is:

```text
Operon records and reproduces what ran.
The learning loop decides what to test and whether it helped.
```

#### Illustrative capsule

```yaml
capsule_id: replay_buildstacks_ticket_2
episode_id: buildstacks-ticket-2
kind: build-ticket
seed:
  repo: buildstacks-dev/buildstacks.dev
  commit: abc123
input:
  ticket_ref: github:#2
system_fingerprint: sys_01ABC
artifacts:
  - contract-comment
  - branch
  - pull-request-23
outcome:
  merged: false
  review_cycles: 3
  cost_usd: 266.41
  human_decisions: 42
side_effect_policy:
  network: fixture_only
  publishing: forbidden
  deployment: sandbox_only
replayability: partially_replayable
missing:
  - trusted_expected_outcome
  - external_registry_fixture
```

Capsules should classify as `replayable`, `partially_replayable`, or `non_replayable`. Build episodes are usually easiest because Git provides a strong state snapshot. Support and Marketing need synthetic channels or fake publishing destinations; SRE and deployment work need disposable services, staging, simulated incidents, or shadow execution. Replay must never repeat an irreversible production side effect.

Most capsule fields can be assembled automatically. An eval-builder agent may draft missing fixtures, expected outcomes, rubrics, or graders, but an independent reviewer—and a human for important or ambiguous cases—must validate them before the capsule becomes a trusted eval.

### 13. Keep capsule capture deterministic and token spend selective

The `ReplayCapsule` itself should be overwhelmingly deterministic software. The expensive operation is executing behavioral replays with real agents, not recording the episode.

| Activity | Deterministic software | Model tokens |
| --- | --- | --- |
| Assign episode ID and record input | Yes | None |
| Record commits, artifacts, config, permissions, turns, gates, and outcome | Yes | None |
| Assemble and validate capsule manifest | Yes | None |
| Deduplicate and check replayability | Mostly | Optional |
| Infer a likely lesson or cause | Rules first | Often useful |
| Draft intervention and qualitative rubric | Partially | Often useful |
| Execute control and treatment replays | Software orchestrates | Dominant token cost |
| Grade tests and gates | Yes | None |
| Grade qualitative behavior | Sometimes | Optional model cost |

The always-on rule should be:

> Capture everything necessary for replay deterministically at the episode boundary, but spend model tokens only after deterministic filtering identifies a candidate worth evaluating. The ReplayCapsule should be cheap; replay execution is the metered resource.

A simplified cost model is:

```text
learning cost
≈ distillation
+ independent review
+ repetitions × (control episode cost + treatment episode cost)
+ qualitative grading
```

For illustration, if one production-equivalent episode costs $10, one paired control/treatment replay is roughly $20 before distillation and grading; three paired trials are roughly $60. Actual costs depend on the participating roles and passes. The system must not replay every completed episode.

Use a progressive spending funnel:

```text
every live episode
    ↓ zero-token deterministic capture
completeness, deduplication, recurrence, and eligibility checks
    ↓
candidate generation and independent review
    ↓ small model spend
targeted role-level behavioral eval
    ↓
full paired episode replay
    ↓ larger model spend
small live episode canary
```

Required cost controls:

- A separate monthly learning/evaluation budget.
- Per-candidate replay and repetition caps.
- Maximum model-powered distillations and experiments per period.
- No model turn when deterministic prechecks find no actionable evidence.
- Targeted behavioral evals before full episode replay.
- Early stopping when the held-in case fails or a safety guardrail trips.
- Full replay only after policy or human authorization.
- Cost per experiment and cost per accepted improvement in reports.
- A requirement that expected benefit justify evaluation cost.

### 14. Add first-class redesign contracts

The redesign should define and connect at least these contracts before implementation begins:

```text
EpisodeRecord
  └── SystemFingerprint
  └── turns, artifacts, outcomes, human observations

ReplayCapsule
  └── reproducible seed, isolation policy, expected outcome, grader

CandidateArtifact
  └── evidence, proposed destination, scope, tier

InterventionRecord
  └── exact reviewed change, activation, affected episodes, rollback

ExperimentRecord
  └── hypothesis, control, treatment, eligibility, metrics, guardrails

EvalResult
  └── improved | regressed | inconclusive | not_evaluatable
```

The redesign must also state which component owns each write, where the artifact lives, how it is content-hashed and versioned, which operations require human approval, and how crash recovery and idempotency work.

## Recommended sequencing

I would revise the milestones to:

1. **Rebase after proportionality.** Convert overlapping Preflight work into conformance tests and freeze a post-proportionality baseline.

2. **Capture-only.** Exact-once evidence projection, the complete episode-linked human review/correction workflow, read-only reports, and closure of the agent-direct active-memory path.

3. **Episode and replay substrate.** Add `EpisodeRecord`, `SystemFingerprint`, `ReplayCapsule`, replayability classification, side-effect isolation, and deterministic capsule finalization.

4. **Experiment substrate.** Add `InterventionRecord`, `ExperimentRecord`, eval fixtures, trusted graders, outcome metrics, and control/treatment comparison.

5. **Manual governed activation.** Candidate review, content-bound human approval, deterministic publisher, immutable versions, resolver, disable, and rollback.

6. **Offline evaluation and human-started canary.** Deterministic and targeted checks first, paired episode replay second, and a sticky episode-level canary only when safe.

7. **Scheduled distillation.** Add the distiller and reviewer after deterministic prechecks show actionable evidence exists, with learning-budget and candidate-volume limits.

8. **Earned automation.** Require decision agreement plus low harmful-promotion rates, demonstrated outcome improvement, and no guardrail regressions. Agreement alone is insufficient.

A convincing end-to-end acceptance test would demonstrate:

```text
seeded failure
→ trusted evidence
→ finalized ReplayCapsule
→ candidate
→ independent review
→ executable ExperimentRecord
→ paired baseline/treatment replay
→ held-in improvement
→ held-out non-regression
→ bounded episode-level canary
→ promotion
→ later regression
→ disable/rollback
```

## Bottom line

This is a strong design for governed, non-parametric agent-system improvement. It directly addresses the memory-poisoning and uncontrolled self-modification risks we discussed. Once the experiment contract, episode-level assignment, eval runner, cross-destination intervention lineage, and specification inconsistencies are resolved, Operon will have a credible continuous-improvement system without needing model-weight training.

As currently written, I would call it a **governed learning and change-management loop**, not yet a proven self-learning loop.
